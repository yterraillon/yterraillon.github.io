01État des lieux

Quatre rôles se sont empilés au fil des travaux. Chacun a été posé là où il y avait de la place, pas là où il avait du sens.

RôleOù il vit aujourd'huiSymptôme
Landing perso dimin.devindex.html + app/css/Vestige d'une « Feature Sliced architecture », output.css committé à la main
Site vitrine enbref.apppages/en-bref/Un niveau pages/ qui ne sert plus à rien dès qu'il y a plusieurs sites
Données publiéescdn/en-bref/data/latest-recap.jsonUn bot écrit ici chaque jour et noie l'historique
CDN d'assetscdn/*Mélange assets externes, images de la landing et données mutables

Ce que l'analyse remonte

  • ~750 commits sur 789 sont des écritures de bot — Updated latest Recap, Muscle Routine, Meal selection — sur trois fichiers JSON. Les 40 commits humains sont introuvables. Le poids n'est pas un problème (.git = 3,7 Mo) ; la lisibilité, si.
  • the-coding-nook/ est l'ancienne marque. Son logo.png et son hero.jpg servent aujourd'hui la landing Dimin.dev. Le nom du dossier ment.
  • Trois nommages pour une même app : en-bref (dossiers), enbref.app (domaine), EnBrefLogo_… (fichiers).
  • Ni CNAME, ni workflow GitHub Actions dans le dépôt. Le bot pousse via l'API GitHub, probablement depuis n8n.
  • Deux doublons exacts (vérifiés au md5) dans cdn/en-bref/ : le logo noir sur blanc existe en double, l'artwork iTunes aussi.
  • Deux bugs de surface : pages/en-bref/index.html:16 utilise des classes Tailwind alors que la page ne charge jamais output.css ; le footer de index.html pointe sur href="#" alors que les pages légales existent.

02Le vrai problème n'est pas le multi-rôle

Un dépôt pour quatre choses n'est pas un défaut ici : les quatre partagent le même mode de publication — statique, public, versionné, gratuit. Ce qui coince, c'est que rien dans l'arborescence ne dit qui est qui, et que le rôle « données mutables » pollue le rôle « code ».

La ligne de séparation n'est donc pas le domaine, c'est la fréquence d'écriture.

RôleÉcrituresAuteurEmplacement cible
Sites statiquesrares, manuelleshumainsites/ sur main
Assets CDNrares, manuelleshumaincdn/ sur main
Données publiéesquotidiennes, automatiquesbotbranche data
Deux limites de GitHub Pages à assumer, pas à contourner. Un seul domaine custom par dépôt : dimin.dev et enbref.app ne peuvent pas coexister en racine sans un proxy devant. Et aucun contrôle du Cache-Control (~10 min imposées) ni de redirections serveur : pour le rôle CDN, cela veut dire pas de renommage silencieux, et versionner par le nom de fichier quand un asset doit changer.

05Pourquoi une CI devient nécessaire

GitHub Pages en mode « deploy from a branch » ne sert qu'une seule branche. Dès lors que les récaps vivent sur data, il faut passer en mode « GitHub Actions » pour assembler les deux sources en un artefact unique. Ce n'est pas gratuit : c'est la contrepartie directe de l'isolation des écritures de bot — et elle rend trois services au passage.

  • Tailwind est compilé par la CI : fini le output.css régénéré et committé à la main.
  • L'arborescence source est découplée de l'arborescence d'URLs.
  • Ajouter un site devient déclaratif : un dossier, une ligne de workflow.

deploy-pages.yml — sur push vers main et data

  1. checkout de main
  2. npm ci, puis Tailwind CLI pour chaque site → dist/<site>/css/site.css
  3. copie des trois sites/* vers leur sous-chemin dans dist/
  4. copie de cdn/** → dist/cdn/
  5. checkout de la branche data dans dist/data/
  6. upload-pages-artifact + deploy-pages

Plus un déclencheur workflow_dispatch pour redéployer à la main.

06Routage des domaines

Point à vérifier avant toute migration : aucun CNAME n'est versionné, donc la configuration réelle vit uniquement dans les réglages GitHub et le DNS. L'arborescence cible fonctionne dans les deux scénarios — c'est précisément pourquoi enbref.app est mappé sur un sous-chemin plutôt que sur une racine.

Scénario A · par défaut

Un seul domaine

CNAME = dimin.dev. Le site En Bref vit sur dimin.dev/enbref/, et enbref.app redirige au niveau du registrar. Aucune infra supplémentaire.

Scénario B · deux domaines

Cloudflare devant

enbref.app proxifié, avec une règle de réécriture enbref.app/* → …github.io/enbref/*. L'arborescence ne bouge pas d'un octet ; seule la config Cloudflare s'ajoute.

À confirmer avant de committer quoi que ce soit

  • Settings → Pages : source actuelle, domaine custom configuré, état HTTPS
  • DNS de dimin.dev et enbref.app (enregistrements A / CNAME)
  • Le job n8n qui écrit latest-recap.json : token, branche et chemin cibles
  • Les consommateurs réels des URLs /cdn/… : app En Bref iOS, app Checquy, workflows n8n
  • Les URLs de pages légales déclarées dans App Store Connect

09Vérification

  • Local — npx serve dist après avoir rejoué le workflow à la main : /, /enbref/, /enbref/legal/privacy-policy.html, /ampr/, une image /cdn/checquy/…
  • Liens morts — un passage de lychee sur dist/, zéro 404, en particulier sur les chemins CDN réécrits
  • Déploiement — pousser sur une branche de travail, workflow au vert, puis merger et contrôler la production
  • Chaîne des récaps — déclencher le job n8n : le commit atterrit sur data et non sur main, le workflow se redéclenche, le JSON est à jour
  • Non-régression CDN — un curl -I à 200 sur chaque ligne de docs/CDN.md
  • Test final de la cible — dérouler ADD-A-SITE.md sur ampr : si la recette demande de toucher autre chose que sites/ampr.app/ et une ligne du workflow, la cible a raté son but

10Ce que ce plan ne fait pas

Réécrire l'historique de main pour effacer les ~750 commits de bot. C'est tentant et faisable avec git filter-repo, mais le dépôt ne pèse que 3,7 Mo : le gain serait cosmétique, alors que le coût est réel — force-push, hashes invalidés, clones cassés. La branche data assainit l'historique à partir de maintenant, ce qui est le seul horizon qui compte.

Sortir le CDN dans un dépôt séparé. Le rôle CDN n'a ni le volume, ni le trafic, ni le cycle de vie qui justifieraient un second dépôt et une seconde chaîne de déploiement. Il devient simplement, dans celui-ci, un contrat public explicite et documenté.
